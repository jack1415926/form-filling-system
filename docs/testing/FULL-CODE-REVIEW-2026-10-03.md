## 1. [P2] 改回基线的字段仍被提交，可能覆盖外部修改

位置：`frontend/src/App.tsx:65`、`:92`；`frontend/src/MaterialEditor.tsx:34`、`:38`、`:57`—`:60`。

概述和物料使用集合累计所有触碰过的字段，保存时把这些字段的当前值全部提交。字段恢复原值后不会从集合移除，处置格的字段集合也一样。因此所谓局部 PATCH 实际包含已经撤回的修改，干净状态也无法准确恢复。

已复现的概述过程：

1. 打开标题为 `original-title` 的申请。
2. 标题改为 `temporary-title`，再改回 `original-title`。
3. 模拟另一个窗口保存 `external-title`，原账号重登；脏表单按保护规则保留本地输入。
4. 当前窗口仅修改区域为 `local-region` 后保存。

实际 PATCH：

```json
{"title":"original-title","affected_region":"local-region"}
```

模拟服务器中的外部新标题被覆盖为旧标题。用户的最终修改只有区域，标题已经撤回；这是请求负载导致的覆盖，不是后端局部 PATCH 或行锁失效。

物料也已通过实际控件复现：料号临时修改后撤回，只想保存描述，实际请求仍为：

```json
{"material_no":"original-material","description":"local-description"}
```

服务器的 `external-material` 被覆盖。处置字段具有相同累计集合逻辑，本轮未单独操作每个处置格。

修复方向：按已保存基线计算实际差异，用同一结果决定 dirty 和负载。另行保留“上次提交结果未确认”的字段；不能简单清空已触碰集合，否则会重新引入响应丢失后撤回/清空无法重试的问题。当前问题页与 EMC 的差异/未确认字段处理可作为已有模式参考。

最小回归：撤回字段不提交、外部字段保持、普通恢复原值解除离开保护、未知保存结果下恢复原值仍可正确重试；覆盖概述、物料基础字段与处置字段。

## 2. [P2] 子页面把旧概述缓存标记成新版本，丢弃内容更新的详情

位置：`frontend/src/QuestionEditor.tsx:48`、`frontend/src/EcrEditor.tsx:88`、`frontend/src/EcoEditor.tsx:88`、`frontend/src/EmcEditor.tsx:46`；读取比较位于 `frontend/src/App.tsx:193`。

四处保存回调均以旧申请详情 `current` 为内容，仅把 `updated_at` 替换成子页面响应时间，然后写回完整详情缓存。这个子页面响应并未包含最新概述字段，新的时间戳并不能证明旧概述内容也是最新的。但详情 GET 会将这个合成对象当成完整的新版本比较。

问题页已复现如下响应顺序：

1. 当前详情缓存：`original-title`，时间 09:00:03。
2. 模拟外部更新标题为 `external-title-after-read`，时间 09:00:04。
3. 原账号重登触发详情 GET，读取到新标题和 09:00:04，暂缓响应；问题页读取正常完成。
4. 问题备注保存成功，响应时间 09:00:05。回调把旧标题与新时间拼成详情缓存。
5. 释放步骤 3 的真实读取结果，再切回概述。

实际页面仍显示 `original-title`，模拟服务器为 `external-title-after-read`。包含更新标题的 GET 被当成旧响应丢弃，页面却显示新保存时间。切换页签不能修复，因为共用详情查询未失效、缓存被视为新鲜。

ECR、ECO、EMC 采用相同代码模式，已逐处核对；本轮完整交错复现入口为问题页，未将它写成四个独立浏览器通过/失败结果。

修复方向：子页面保存后使完整详情查询失效并重新读取，或将展示用的最近保存时间与完整详情版本分开保存。不要给旧完整对象升级版本时间；保持已有脏输入和请求交错保护。无需增加并发版本控制平台。

最小回归：外部概述修改 → 暂缓详情 GET → 子页保存 → 释放 GET，最终概述必须显示已读取的新字段；覆盖四个写入回调及反向返回顺序。

## 3. [P2] 物料列表刷新后，干净抽屉仍使用打开时快照

位置：`frontend/src/MaterialEditor.tsx:114`、`:120`；表单初始化位于 `:54`。

打开抽屉时把整条物料保存到 `editor.material`，后续仍把这个对象传入 MaterialForm。列表查询更新不会替换该快照，Ant Design 的 initialValues 也不会自动重新初始化表单。与 ECR/ECO 已处理的干净抽屉同步不同，物料页没有采用最新物料及更新基线的逻辑。

已复现：

1. 打开料号/描述为 `original-material` / `original-description` 的物料，不做修改。
2. 模拟外部保存 `external-material` / `external-description`。
3. 从抽屉使用原账号重新登录，等待物料列表完成刷新。

实际列表已显示 external 两个值，抽屉仍显示 original 两个值，并处于“已保存”状态。证据截图为忽略文件 `.local/review-material-stale.png`。此项本身确认的是显示及基线不一致；直接覆盖问题另由第 1 项的实际 PATCH 复现证明。

修复方向：按稳定物料 ID 取得列表最新记录，并仅在表单无修改、无保存中请求、无待确认结果时同步表单与基线。不能无条件更新 initialValues 或重挂载表单，否则会丢失脏输入。原有失败保留输入及稳定 UUID 去重继续保留。

最小回归：干净重登同步基础字段与处置；脏重登保留输入及原基线；未知结果保留；后续只修改一个字段不回写其他旧字段。
