## 方案目标与流程

基础链路扩展为：**新建 → 填写与保存 → 选择指定／公开审核并提交 → 查看待审核申请 → 自由文字反馈 → 达到批准条件**。

申请采用四个状态：**草稿draft → 待审核pending → 已批准approved**，或 **待审核pending → 待修订returned → 新一轮pending**。不设置独立的“填写完成”状态或“发布”操作。

草稿支持填写、修改、保存和重新打开，填写员只能查看本人申请，不能查看其他填写员的申请。提交前保存表单并执行既有校验；提交时选择一种审核方式，成功后锁定表单、审核方式及指定人员名单，登录后的审核待处理提醒按2026-10-08确认范围提供。

| 审核方式 | 提交条件与可见范围 | 通过条件 |
| --- | --- | --- |
| 指定审核 | 至少指定一名审核员；申请者查看本人申请，所选审核员获得各自任务，其他填写员不可见 | 所选审核员全部批准；个人批准后不再列入其待处理任务 |
| 公开审核 | 无须指定人员；申请者查看本人申请，申请进入审核员的公开审核列表，其他填写员不可见 | 两名不同审核员批准后通过；重复批准只计一次，不要求所有审核员批准 |

审核动作只允许具有审核员身份且有权访问本单的人执行，后端校验权限；公开审核不向填写员开放其他人的申请或审核权限。任一方式达到通过条件后，申请进入已批准。

反馈初版统一为申请内的自由文字记录：意见、想法、疑问、解释或补充说明均可追加，不分类、不作为批准，也不自动改变状态。待审批期间，申请者及有权审核本单的人可以追加反馈；已批准过本单的审核员，在申请仍待审批时可以继续反馈。达到最终通过条件后结束追加，表单、审核结果及反馈全部只读。保存作者、时间及内容，按时间顺序展示，不增加编辑、删除、附件或嵌套讨论。

## 最小实现边界

- 沿用现有登录功能，区分填写员与审核员身份，由后端校验本单的访问及审核权限；指定模式从审核员中选人，公开模式不选人。不增加复杂账号管理，管理员规则维护暂不纳入 MVP。
- 同一账号只保留一个有效的数据库登录会话，新登录成功后使旧会话失效；同一浏览器共享 Cookie 的窗口属于同一个登录会话，不按窗口数量限制。
- 提交前保存表单并执行既有校验；指定模式至少选一名审核员，公开模式无须选人。提交后不能修改表单、审核方式或指定人员名单。
- 指定模式全部指定审核员批准后通过；公开模式两名不同审核员批准后通过，不增加抢单或任务领取流程。
- 填写员始终只能查看本人申请；审核员只能访问指定给自己的申请或公开审核申请，不能因登录或超级用户身份获得任意草稿的业务访问权限。
- 反馈按时间顺序展示，可笼统记录意见、想法或说明；追加反馈不改变审批状态，不增加类型分类、编辑、删除、附件或嵌套讨论。
- 锁定由后端统一执行，覆盖所有表单保存接口；重复批准不产生重复记录，同时批准时正确判断是否全部完成。
- 支持退回和按轮再次提交；不增加最终拒绝、撤回、撤销批准、Excel导出或其他功能。

保存每名审批人的批准结果及时间属于本次功能所需数据，不再排除基本审批及审批记录。完整操作日志、字段修改历史、历史版本、并发版本控制、通用动态表单、模板版本管理、扩展字段机制、复杂角色权限、手机端专项适配、历史 Excel 导入和正式模板导出继续排除。

## 数据存储与 ER 补充

数据库采用 MySQL Community Server 8.4 LTS，表使用 InnoDB，字符集使用 `utf8mb4`。后端继续采用 Django 和 Django REST Framework，通过 Django 内置 MySQL 后端及 `mysqlclient` 驱动访问数据库；其他前后端技术选型不变。

编号规则：草稿保存时，非空 ECR 编号和非空 ECO 编号分别必须唯一，空编号允许重复。该规则的实现状态和行动项统一见 [当前进度](../README.md#当前进度)，确认规则不代表校验和数据库约束已落地。

按原技术方案设计，以 `change_request` 为主记录，物料、处置、问题回答、行动、执行计划和实质性变更评估数据分别关联保存。这是目标数据结构，实际实现范围见 README。固定问题、行动定义及判断规则作为系统配置统一维护，不随每项申请重复保存。

主记录保存申请者、申请状态及审核方式。按轮冻结所选审核员名单、提交时基本信息和时间；两种模式均保存该轮实际批准人员及批准时间、退回人／时间／原因；反馈记录关联轮次、作者、内容和时间。提交批次已新增审核方式／提交时间、指定审核关联与提交接口；批准、退回、按轮重提及反馈接口已接入；技术交付不等于业务验收。

一项申请与审核记录为一对多关系，指定模式每名所选审核员对应一项任务，公开模式按实际批准保存记录；一项申请与反馈记录为一对多关系。具体表名及字段在对应开发批次确定。数据库约束和事务处理保证同一轮次与审核员组合不重复，并发批准时按本单审核方式正确判断是否达到通过条件。

提交、批准和留言写入需在数据库事务内校验申请状态；涉及状态转换时锁定对应申请主记录，使表单保存、提交锁定、最后一人批准和结束留言正确衔接。批准记录设置轮次与审核员的组合唯一约束。验收时使用实际 MySQL 数据库验证并行批准、重复批准及提交后的保存锁定。

现有 ER 图不包含新增审批记录和留言记录，也不代表本次完整实现范围。图内模板版本等属性不改变本次排除版本管理的边界。

## 验收要求

使用一名申请者、至少两名审核员及另一名填写员，分别验证指定与公开模式：

1. 申请者新建草稿，填写八张工作表并保存；重新打开后恢复已填内容，既有规则正确执行。
2. 提交前完成保存及既有校验。指定模式未选人不能提交，至少一人可提交；公开模式不要求选人。
3. 提交后为待审批，不能修改表单、审核方式或指定名单；后端拒绝所有相关保存接口的修改请求。
4. 指定模式仅所选审核员获得任务，未指定审核员不能批准；选择一人时该人批准即通过，选择两人时第一人批准后仍待审批、第二人批准后通过。
5. 公开模式进入审核员公开列表；第一名审核员批准后仍待审批，第二名不同审核员批准后通过，不要求所有审核员批准。
6. 另一名填写员不能通过页面或API看到该申请；批准接口同样拒绝填写员。
7. 待审批期间申请者及有权审核本单的人可追加任意自由文字反馈；已批准过本单的人仍可反馈，作者、时间和内容正确展示，反馈不会自动改变状态。
8. 达到通过条件后为已批准，表单、审核结果及反馈只读，不能再追加反馈。
9. 重登及重开恢复审核方式、指定名单、实际批准人员／时间和反馈。
10. 两种模式重复批准只计一次；并行批准最终状态正确，最终批准与反馈并行时正确执行状态锁定。

## 2026-10-05 审核、退回与再次提交确认

审核员查看整份当前表单。个人通过不等于整单已批准：指定模式全部所选人员通过，公开模式两名不同人员通过。pending时任一有权审核员可退回整单，包括已个人通过者；原因必填。退回结束本轮，returned允许本人修订但不能删除申请，审核员不查看修订中的整表。双方可继续追加自由文字反馈。有权审核员通过“退回沟通”进入当前退回轮次，不要求已个人批准；重新提交后旧轮移出该入口。

再次提交默认沿用审核方式／人员但允许更改，重新校验有效账号、标题及ECR等条件，并开启独立新轮；上一轮批准不计入新轮。新轮权限重算，旧人员未获新权限不得看新表单或新反馈；新轮有权人员可看以前意见，旧轮过程只读。保留每轮方式、名单、通过、退回原因和反馈，不保存完整旧表单快照。approved是MVP终点，不再打开。

批准、退回和反馈请求带所查看轮次，过期轮请求409；提交UUID仅确认同一次提交，不能用旧请求开启新轮。所有状态转换及表单保存／反馈共用申请行锁，最后批准与退回先成功完成者生效，另一方冲突刷新。前后端草稿／退回可编辑、待审核／批准只读，审核员始终不具备填写权限。审核请求在途或当前待审核轮次操作结果未确认时，所有表单返回入口应阻止离开，保留查询和原请求重试入口；结果确认后恢复导航。上述流程已技术实现，当前版本业务复验仍待完成。

新增验收：已个人通过者能在pending退回；退回理由为空拒绝；returned八表可修订但禁删，审核员表单GET拒绝；新轮旧批准为零、改名单后旧人员隔离；旧轮写入拒绝；returned交流和历史作者／时间正确；approved不可退回／反馈；重复／并行批准及最终批准与退回竞争正确。

### 审核修改意见

- [x] 审核员查看已提交申请，先列多条具体问题，标明所属页签及必要的题号／物料信息；确认后一次性提交意见并退回整单，而非每条立即退回。正式意见保留提出者、申请和审核轮次。
