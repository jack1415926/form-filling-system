## 问题回顾

2026-10-07首次整理：只读筛查本地登记的10个项目主会话及26个自动审批辅助会话，回顾主会话保留的审查结论和修复回复，并对照相关验证文档去重。范围为2026-09-30至2026-10-07；自动审批记录用于区分工具／执行限制，不作为产品Code Review结论。这是历史回顾；本次补充各问题的场景、成因和处理思路，没有重新复现缺陷或运行业务测试。

### 登录、身份与输入保护

- **登录成功后页面仍停在登录页。** 服务器已经接受账号密码，但前端没有正确保留登录后的用户状态，用户看到的结果仍像未登录。这个问题需要同时检查认证响应和页面缓存更新，不能只凭登录接口成功判断完整登录流程正常。登录后的缓存处理影响当前用户状态；调整为只清理业务缓存并更新当前用户，恢复正常进入工作台。

- **共享窗口重登后持续CSRF失败。** 同一浏览器两个窗口共享Cookie，一个窗口重登会改变当前会话及令牌，而另一个窗口可能仍保存旧令牌。旧窗口反复点击保存也无法自行恢复，容易被误认为账号或业务校验失败。旧页面沿用过期令牌；写请求改为读取当前Cookie中的CSRF令牌。

- **退出失败仍清掉未保存提醒。** 页面有未保存内容时发起退出，若请求失败，用户实际上仍留在编辑页。此时提前清理修改状态会让后续离开失去提醒，因此必须以真正完成的退出结果决定是否清理。清理时机过早；改为真正离开或退出成功后才清除，失败保留输入和提醒。新建、保存与退出请求互相干扰也通过请求期间控件互斥处理。

- **后台读取失败卸载编辑器，导致未保存输入丢失。** 例如用户正在物料抽屉输入，查询缓存过期后网络重连触发后台GET，返回503就把整个编辑页面替换成错误页。服务器没有删除数据，但组件卸载让尚未提交的文字直接消失，属于前端数据丢失。有缓存数据时改为保留页面及抽屉，只显示错误和重试入口；仅首次无数据加载失败才显示独立错误页。

- **会话失效或换账号时，输入保护和身份隔离互相冲突。** 同账号在另一处登录会使旧会话失效，旧页面若直接跳回登录页会丢输入；反过来，无条件保留缓存又可能在切换账号后展示前一账号的申请。因此网络故障、原账号失效和实际身份变化必须分别处理。401失效保留原账号输入并提供重登；确认换账号时隔离业务缓存及当前申请，避免新账号看到旧账号详情。

- **共享Cookie切换账号后，旧窗口可能把新申请写进另一账号。** 旧窗口仍显示账号A，但Cookie已被另一窗口切换成B；在用户信息刷新前点击新建，服务器就按B创建申请。这不是服务器越权，而是页面显示身份与实际认证身份不一致，资料会归到用户没有预期的账号。前端缓存隔离不能覆盖身份刷新前的写请求；增加页面预期账号，由后端核对实际登录身份，不匹配时拒绝操作。

### 保存、错误提示与未知结果

- **整表或“曾编辑字段”提交覆盖外部新数据。** 一个典型场景是标题被临时修改后又撤回，另一窗口随后保存了新标题，本窗口仅想修改区域，却把旧标题也带进请求。局部PATCH并不天然安全，关键在于提交的是实际差异，还是累计记录的操作痕迹。先改为局部PATCH，后续审查又发现撤回到原值的字段仍被提交；最终按保存基线计算实际差异，同时保留结果未确认字段用于重试。

- **物料新增已入库但响应丢失，重试重复创建。** 第一次POST在数据库中已经成功，浏览器却只看到了失败；再次点击保存又按新增执行，从而出现两条相同物料。必须识别同一次创建尝试，既避免重复写入，也保留正常新增相同料号的业务能力。同一次新增使用稳定UUID，后端按申请与UUID去重；不能按业务允许重复的料号去重。

- **响应丢失后改回原值，页面误报已保存。** 例如原备注为空，服务器已保存新备注但响应丢失，用户再清空输入。界面与旧基线一致，却与服务器实际值不同；如果此时禁用保存按钮并允许离开，用户就无法把清空操作真正提交。旧基线不能证明服务器当前状态；保留未确认字段和离开保护，重试提交当前值，包括明确清空。

- **问题页刷新／关闭缺少未保存提醒。** 页签切换已有确认框，容易让人以为刷新和关闭也受保护，但这两条路径使用不同机制。进入问题页后，概述和物料里的局部监听已经卸载，问题页输入没有对应的浏览器离开保护。监听原先放在各页局部，切换后可能卸载；统一放到申请编辑容器，覆盖修改中及保存中的页面。

- **嵌套处置错误显示成`[object Object]`，保存错误位置也不明显。** 处置接口的错误可能嵌套到具体位置及字段，简单拼接顶层对象会丢失叶子原因。用户既不知道哪一格有问题，也可能因错误只出现在页面顶部而看不到反馈，导致反复提交。递归提取字段路径和具体原因，持续显示在保存操作附近。

- **异常成功响应导致错误确认并丢失输入。** HTTP 200不代表已经拿到合法的业务记录；物料新增返回空对象或数组时，原界面仍提示成功并关闭抽屉。正确的确认点应是响应能够证明本次操作得到预期记录，而不是仅凭状态码。先拒绝不可解析的成功响应，后续补齐物料记录结构、ID及类别校验；无效响应按结果未确认处理，保留输入、抽屉和UUID。

- **请求无响应导致保存和导航永久锁定。** 共享保存队列里，一个始终pending的请求会让后续手动保存一直等待，同时阻塞页签和重登入口。设置期限也不能把写入判成失败，因为服务器可能已经提交，只是客户端没有收到确认。API全流程增加30秒总期限，覆盖CSRF、主请求和正文读取；写超时表示结果未确认，迟到响应不能再更新缓存或解除保护。

对应[问题页修复](testing/QUESTION-REVIEW-FIXES-2026-10-02.md)、[全项目审查](testing/FULL-CODE-REVIEW-2026-10-03.md)和[保存恢复修复](testing/SAVE-RECOVERY-FIXES.md)。

### 读取一致性、缓存和表单同步

- **物料及处置读取混合了不同版本。** 基础物料与处置预取是两次查询，若中间发生并发PATCH，就可能返回旧料号搭配新处置备注。写事务虽然原子完成，读取结果仍可能是数据库里从未共同存在过的组合，影响用户判断。两次查询之间可能穿插保存；读取沿用申请行锁，与写入串行，保证返回共同存在过的内容。

- **旧GET／PATCH迟到，覆盖更新后的内容和保存时间。** 例如较新的GET已经显示负责人B，较旧的保存响应随后返回，又把列表退回负责人A；申请时间也可能一起回退。网络响应的到达顺序并不等于数据版本顺序，保护需要同时覆盖读取和保存回调。概述、问题、ECR、ECO、EMC相关读写与缓存入口统一选择最新响应，保留微秒精度和时区顺序。

- **干净表单或抽屉仍显示打开时的旧快照。** 原账号重登后列表已刷新，打开的抽屉却仍保留旧负责人或物料描述，并显示已保存。Ant Design的initialValues也只负责初始化；如果不主动同步，用户必须关闭重开才能看到新内容。概述显式同步Ant Design字段，物料／行动抽屉采用最新记录；有脏输入、在途请求或未知结果时继续保护本地内容。

- **编辑期间收到新读取，撤回修改后却不再采用它。** 用户有本地修改时保护输入是正确的，但新读取已经被标记为见过。等用户把输入撤回旧基线，页面恢复干净，新数据却不会再次应用，形成明明已读取最新值仍显示旧值的状态。一次性`seen`标记提前把新数据算作已处理；改为保护解除后重新判断最新读取。

- **子页只更新旧申请缓存的时间戳，旧内容被伪装成新版本。** 问题或行动保存响应不包含完整概述，却将旧标题与新updated_at组合进缓存。之后真正包含新标题的详情GET反而可能被判为旧响应丢弃，说明版本时间必须与它实际描述的内容对应。保存后重新读取完整申请，不把旧概述与新时间拼成完整记录。

- **服务器已删除的处置格被旧表单重新写回。** 服务器删除某个位置后，新响应不再包含该格，但表单的合并更新不会自动删除原值。用户只修改描述，保存时旧NA和备注却再次进入PATCH，相当于无意恢复了已删除的处置。`setFieldsValue`只合并字段，缺失格未清空；同步干净表单时明确清空已删除位置，同时保留脏输入保护。

### 日期、实质性评估与提交页面

- **日期只输入一部分，被误当作清空保存。** 例如已有完整日期，只删掉年份，或从空值开始只键入年份，控件可能返回空字符串而不是完整ISO日期。用户还在编辑，却被自动保存为null；这是不完整输入与明确清空混淆造成的。原生日期控件可能value为空而badInput为真；保留原值、提示并阻止保存，只有明确清除才提交null，同时补齐键盘和失焦检查。

- **实质性评估首次残缺响应污染缓存，正常重试无法恢复。** 首次GET没有旧基线可比，合法assessment配上空charts／questions也曾被接受。残缺结构一旦成为基线，后续正常的37题响应反而因字段集合不同被拒绝，所以完整性校验必须独立于旧缓存存在。首次读取也独立校验固定主项、37题标识、分组和必要字段，在写缓存前拒绝残缺数据。

- **新增迁移后，旧迁移测试只恢复到旧版本。** 迁移测试会临时把数据库切回历史结构，再验证升级过程；若finally仍硬编码恢复到0010，新增0011后就会留下缺表的测试库。这是测试准备和清理问题，不是业务迁移本身的数据丢失。测试库缺少新表；清理阶段改为恢复全部迁移叶节点，保留原业务断言。

- **提交页遗漏已填写的ECO编号。** 用户在概述中已经填写ECO，但进入提交摘要和最终确认时看不到，容易怀疑保存失败。排查确认接口和响应校验已经包含该字段，因此只需修正展示，不应额外增加必填条件或修改数据库。接口已有数据，界面摘要与确认弹窗漏展示；补齐两处显示，不改变提交必填规则。

- **提交结果恢复后仍被旧unknown状态锁住。** 两种路径都出现过：未知请求重试收到明确400后无法重新选人；GET已经确认pending，迟到POST错误却又设置unknown。旧错误不应推翻已确认的提交，明确拒绝后的草稿状态也需要重新核对后恢复操作。重试明确拒绝，或GET已确认提交但POST迟到失败时，恢复逻辑优先采用已确认的新状态；只有结果仍未确认才保留原请求保护。

### 审核与逐条意见闭环

- **退回后，有权但尚未批准的审核员找不到沟通入口。** 指定A、B审核，A退回后，B尚未个人批准，在待处理及已处理列表都找不到申请，但轮次接口仍允许其沟通。接口权限正确还不够，用户必须有能发现该记录的页面入口。增加“退回沟通”列表，按当前轮权限提供入口，仍禁止读取修订中的正文。

- **审核操作在途时，其他表单返回按钮仍可卸载恢复面板。** 批准按钮所在面板的返回已禁用，但只读概述等页签仍调用未检查busy的共享返回函数。点击后审核请求可能仍在服务器完成，页面却丢失查询和原请求重试入口，用户难以确认实际结果。在共享返回函数及八表入口统一检查在途／未知状态，保留查询和原请求重试入口。

- **审核操作失败，主审核区看不到恢复提示。** 批准或退回从主区发起，未知结果提示却放在意见抽屉中，抽屉未打开时用户可能只看到操作受阻。另一个交付时问题是沿用并锁定的审核安排被误算为尚未提交的选择，造成不必要的离开保护。异常或未知结果时自动打开意见抽屉，使恢复入口可见；锁定的原审核安排也不再误算为未提交选择。

- **重提重建意见面板，清空未发送回应。** 已回应的意见仍允许继续输入新文字，但提交页没有检查这一层草稿。重提成功改变轮次后，React key变化重建面板，文字随状态销毁，因此需要在发起重提前处理未发送内容。未发送状态传到提交页，阻止重提；用户发送或明确清除文字后才继续。

- **刷新后旧回应草稿使用新版本号，绕过冲突保护。** 另一窗口已经更新意见，本页仍保存针对旧内容写的回应；刷新只更新服务器版本，发送却取新版本号。后端看到的是最新版本请求，无法知道文字实际上基于旧版本编辑，必须让草稿与编辑时版本一起保存。草稿绑定开始编辑时的版本，刷新不自动提升；发现冲突时保留文字并阻止发送。

- **查询发现已退回、失权或版本变化，未知操作仍锁死导航。** 未知批准后，另一审核员可能已经退回当前轮；查询虽得到returned，但is_current仍为真，旧逻辑就继续冻结。当前轮存在不等于原动作仍合法，应结合状态、权限和版本决定是否还有继续重试的意义。优先核对原UUID确认记录，再判断动作是否仍可执行；已不能执行时保留文字、说明原因并解除导航锁。

对应[审核流程修复](testing/REVIEW-WORKFLOW-2026-10-05.md)和[正式意见闭环及三项P2修复](testing/REVIEW-ISSUES-2026-10-05.md)。以上产品问题均有历史修复记录，不能据此把用户业务验收标为完成。

### 环境、验证与开发过程

- **目录改名后Python虚拟环境仍引用旧绝对路径。** 项目文件可以正常看到，但环境启动器或解释器定位仍指向改名前的位置，导致后端不能启动。应修复运行环境的路径绑定，不把它误判为Django源码故障，也不直接搬运这套环境到新机器。重新定位解释器并重装原依赖；另一台设备应重新创建虚拟环境。见[阶段一环境记录](testing/REVIEW-2026-09-30.md)。

- **MySQL停止导致测试连接10061，旧noreload后端与新源码不一致。** 一个是数据库根本不可连接，测试还没开始；另一个是源码已有新接口，旧进程却仍执行之前的版本。两者都需要先确认运行对象和状态，不能靠修改产品代码去适配未启动服务或过期进程。分别确认服务和项目进程后恢复所需服务、重启当前源码；不能把未执行的数据库测试或旧进程行为当作产品结论。见[全项目审查](testing/FULL-CODE-REVIEW-2026-10-03.md)及[完整流程复验](testing/REVERIFICATION-2026-10-05.md)。

- **测试反复创建用户、计算生产级密码哈希，准备耗时偏高。** 最初怀疑并发等待或建库耗时，实际计时显示大量时间花在重复用户创建和密码验证。优化后仍让请求经过真实认证路径，而不是跳过登录，把速度提升建立在保留原业务断言的基础上。复用测试公共用户，仅在测试类使用快速哈希器，保留真实登录、会话、权限及CSRF断言；生产配置不变。见[测试精简](testing/TEST-SIMPLIFICATION-2026-10-02.md)。

- **辅助浏览器工具反复适配，超出小批业务交付边界。** 编号规则已经形成独立成果后，仍不断处理日期输入、遮罩、按钮定位等辅助脚本问题，演示数据却准备较晚。结果是工具投入挤占交付，用户难以判断真正业务进度；这属于开发过程问题，不等同于产品缺陷。停止扩展并删除不必要的一次性包装，保留业务测试和已有结果；后续先确定小批终点，区分工具失败与产品缺陷，不因定位／动画问题改业务规则。见[阶段一记录](testing/REVIEW-2026-09-30.md)。
