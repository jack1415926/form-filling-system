## 代码复查发现与处理

### 已修复的新建和退出交互缺口

优先级：P2。原页面仅在保存期间禁用退出按钮；新建请求未完成时，退出仍可点击。退出请求未完成时，新建、打开记录、填写和保存也仍可操作。晚到的请求回调可能干扰账号切换，使页面进入旧请求对应的记录或丢失退出过程中新增的输入。

复现方式：在浏览器拦截新建请求，使其保持未完成，检查退出按钮是否可点击。本轮原始结果为：

```json
{"logoutEnabledDuringCreate":true,"bugReproduced":true}
```

修复位置：`frontend/src/App.tsx`。新建或保存期间禁用退出；退出期间禁用新建、打开记录、表单输入、保存和返回。退出失败时恢复操作，并继续保留原输入和未保存状态。

修复后的浏览器回归验证了四类场景：新建禁用退出、列表退出禁用新建及打开、表单退出禁用输入／保存／返回、失败后恢复控件和输入。均通过。

测试实现中第一次使用即时 `isDisabled()` 断言，读取发生在 React 异步渲染完成之前，出现失败。调整为有上限地等待控件状态后验证通过。记录这一点是为了区分测试同步方式和产品缺陷，后续浏览器测试应等待可观察的页面状态，不依赖任意一次瞬时读取。

### 已修复的测试库同名保护大小写缺口

优先级：P1，影响配置误填时的数据保护。原保护只比较测试库名和开发库名的字符串完全相等。Windows MySQL 常见配置中的库名大小写不敏感，仅大小写不同可能仍指向同一库，原检查不能充分保护开发数据。

修复位置：`backend/backend/settings.py`。改为 `casefold()` 后比较；采用保守规则，即使其他环境允许两个大小写不同的库，也不将这种命名组合用于测试。

验证方式：仅加载配置，将 `DB_TEST_NAME` 设置为当前 `DB_NAME` 的大写形式，确认抛出配置错误。验证没有执行迁移、建立数据库连接或删除任何库。

### 已确认的权限和写入控制

- 列表、详情及更新均通过申请者过滤查询，其他普通用户无法读取或修改该草稿。
- 申请者、状态、ID 和时间属于系统字段，保存请求包含这些字段会被拒绝。
- 登录、退出及写入保留 CSRF 校验；本轮补充验证 PATCH 请求同样不能绕过 CSRF。
- 保存在事务中读取并锁定申请主记录，非草稿状态被拒绝；非法输入不会部分保存。
- 数据库约束拒绝三种状态之外的值，权限不依赖前端按钮隐藏。

这些结论限于当前已实现的概述接口；后续增加物料、问题等保存接口时，仍必须复用同一归属和状态校验，并新增对应测试。

### 本轮数据覆盖与异常处理检查

发现并修复：原前端每次保存都发送全部概述字段。两个页面读取同一旧版本后，分别修改标题与区域，后保存页面可能把未编辑的旧标题一并提交，覆盖先保存结果。此前后端的两个局部 PATCH 并发测试不能证明整表前端请求也安全。

现在前端记录有过编辑的字段，只发送这些字段的 PATCH；保存失败时保留字段记录和输入，成功后清除。清空日期发送 `null`，成功回写到日期输入框时转换为空字符串。浏览器真实打开两个独立编辑页面，分别编辑标题和区域，确认请求只带各自字段，数据库同时保留两个结果。

补充修复：HTTP 2xx 但响应不能解析为 JSON 对象／数组时，不再按正常成功处理，而显示未能确认操作结果并保留输入。浏览器用 200 HTML 响应模拟该情形，验证输入仍保留，恢复正常响应后重试可保存。

两个页面同时修改同一字段仍以后保存为准；这是未实现版本／冲突检测时的边界，本轮未新增版本管理。网络中断或响应异常时，前端不能仅凭报错判断数据库是否已写入，应重新打开核对；写请求没有自动重试。

### 接口字段与数据库核对

逐字段核对通过：前端 `Overview` 类型和表单覆盖后端 serializer 的 11 个可写字段；返回的 `id`、`applicant`、`status`、`created_at`、`updated_at` 为 5 个系统只读字段。系统字段不能通过 PATCH 修改。

- 新建请求：允许空对象；后端设置申请者和 `draft` 状态，返回完整记录。
- 保存请求：提交修改过的概述字段子集；日期使用 `YYYY-MM-DD`，清空日期为 `null`；响应仍返回完整记录。
- 列表和详情：字段与前端 `ChangeRequest` 类型一致；列表只含当前申请者的数据。
- 登录：请求为 `username/password`，返回 `user` 和更新后的 `csrfToken`；请求封装保存令牌，页面使用用户信息。
- 当前用户：返回 `id/username/display_name`；未登录返回 401。
- 退出：POST 保留 CSRF，响应包含退出说明和 CSRF 令牌。

Model 与 migration 一致，常规迁移检查没有发现待生成的变更。另行读取实际 MySQL：16 列的名称、类型、长度和可空性与 Model 相符；主键为自增 ID；`applicant_id` 外键指向 `auth_user.id`，Model 使用 `PROTECT`，实际数据库删除规则为 `NO ACTION`；状态 CHECK 约束和 InnoDB／utf8mb4 均存在。

但当前数据库**没有 ECR/ECO 的 UNIQUE 约束，保存接口也没有相应唯一性校验**。原 ER 的 UK 标注与代码之间的缺口，已在本轮向用户确认：草稿保存时，非空 ECR、ECO 编号分别必须唯一，空编号可以重复。按本次提问说明先记录规则，没有实施这一数据库变更；它是本阶段尚未完成项，不是已通过的检查。

### 需要用户手动验证的核心流程

在 http://localhost:5173 使用 `.local/demo-accounts.json` 中的第一个普通账号：

1. 输入错误密码应提示错误；正确登录后进入“我的申请”。另用独立浏览器或隐私窗口登录同一账号，旧端后续读取／保存应被拒绝，未保存输入应保留；同一浏览器共享 Cookie 的窗口属于同一登录会话。
2. 新建草稿，允许部分字段留空；按实际 Excel 填写概述，特别核对编号、负责人文字和日期。
3. 保存后返回列表，再打开、刷新、退出并重新登录，已保存字段应一致。
4. 只修改一个字段保存，其他字段应保留；清空 ECO 日期后保存，再打开应为空。
5. 修改后不保存，返回或退出应提醒；取消应保留输入，确认放弃后重新打开应显示数据库原内容。
6. 新建或保存期间不能退出；退出期间不能继续新建、打开或编辑，失败后可继续操作。
7. 用第二个普通账号登录，不应看到第一个账号的草稿。
8. 可在同一浏览器的两个窗口分别打开同一草稿，分别修改不同字段后保存，两个修改均应保留；在另一个窗口重新登录后，原窗口保存和退出不应因缓存旧 CSRF 令牌而持续失败。同一字段同时编辑仍以后保存为准。
9. 对照实际 Excel，亲自确认业务字段名称、日期展示和保存操作符合使用习惯。助手的自动验收不能代替用户业务确认。
10. 编号唯一性暂不要判定为合格：重复的非空 ECR 或 ECO 目前不会按新规则被拒绝，这一验收项需要待校验和数据库约束实现后再执行；空编号应可重复。

### 人工反馈与单有效会话规则补充

本轮处理中发现用户新增的 `实际人工测试.md` 和截图，只读核对后保留在本机，未代替用户修改或提交。反馈中的“没有删除草稿”和“只有概述页”符合本阶段范围；DELETE 接口按原计划不开放，其他工作表属于后续阶段，没有据此扩展功能。

反馈中的持续 CSRF 失败已作为本阶段缺陷修复。之前缓存的令牌在另一个同浏览器窗口重新登录、Cookie 轮换后失效；关闭另一个窗口不会恢复旧令牌。现在每个写请求读取当前 CSRF Cookie，Cookie 不可读取时再获取令牌，不关闭或绕过 CSRF 校验。持久保存错误已移动到保存按钮附近，并增加可见的失败提示。

此前两个独立浏览器上下文的测试没有覆盖共享 Cookie 的窗口，因此没有发现这个问题。本轮使用专用临时账号，在同一浏览器上下文的两个窗口验证令牌确实轮换；原窗口保存、另一窗口保存、关闭一个窗口后保存及退出均通过。浏览器脚本显式切换正在操作的窗口，避免后台标签页的渲染／操作等待被误记为产品缺陷。

用户另行确认“新登录使旧会话失效”。此规则已在本阶段登录流程实现：复用 Django 的数据库会话及 `user_logged_in` 信号，对同一用户的登录串行处理，轮换并保存新会话，删除该用户旧的有效会话；应用登录和 Django 内置登录均受控。没有新增用户管理页面、角色配置、数据库表或 migration。

单有效会话以服务器会话为单位，不按窗口数限制，也不主动关闭旧端浏览器。新登录后的旧端下一次请求会被拒绝；旧页面缓存的显示和未保存输入仍保留。正式切换后用户需重新登录一次；不在启动时批量清除所有人的旧登录，以免突然影响当前操作。

新增 3 项后端测试分别验证：新登录使旧会话失效、同浏览器重登轮换后仍能保存、Django 内置登录同样执行规则且不影响其他账号。最新总计 19 项全部通过。真实浏览器独立上下文验证旧端 me 返回 401、旧端保存返回 403、新端 me 返回 200，旧端未保存输入保留并显示重新登录提示。
